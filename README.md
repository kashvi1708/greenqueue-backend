# GreenQueue Backend

A FastAPI backend implementing the real GreenQueue scheduling logic:
submit → priority check → carbon check → dispatch or wait → assign
cluster node → run → complete → accumulate impact. Serves the exact
JSON contract the deployed frontend (`https://greenqueue.vercel.app/`)
already expects.

## Endpoints

- `GET /snapshot` — the frontend's one and only data source: jobs, grid
  state (with trend), impact metrics. Matches `GreenQueueSnapshot` in
  the frontend's `src/types/greenqueue.ts` field-for-field.
- `POST /jobs` — submit a job: `{"name": "...", "type": "infer", "urgency": "urgent", "durationMin": 10}`. Returns the created job, already evaluated (urgent jobs dispatch immediately in the response, not on the next tick).
- `GET /health` — plain health check.
- `GET /docs` — interactive OpenAPI docs (auto-generated by FastAPI).

A background loop re-runs the scheduler every 5 seconds so the grid and
job states keep evolving even with nobody hitting the API — this is
what makes waiting jobs eventually dispatch on their own as the
(simulated) grid gets cleaner.

## Architecture notes

- **State is in-memory, single-process** (`app/state.py` — a Python
  list). This is intentional and fine for a hackathon demo. It means:
  restarting the server resets all jobs/impact history, and you can't
  run multiple server instances behind a load balancer without them
  disagreeing. If this needs to survive that later, swap `app/state.py`
  for a real datastore (Postgres, Redis, etc.) — nothing else in the
  codebase needs to change, since `app/main.py` and `app/scheduler.py`
  only touch `state.jobs` / `state.nodes` / `state.impact` as plain
  Python objects, never SQL directly.
- **Carbon intensity is simulated** (`app/carbon.py`), deterministically
  computed from wall-clock time. Swapping in a real grid API
  (electricityMap, WattTime) means rewriting only this file.
- **Field names are camelCase** in `app/models.py`, not the usual Python
  snake_case — deliberate, because the frontend does a raw
  `payload as GreenQueueSnapshot` cast with zero case-conversion.

## Local development

```bash
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Visit `http://localhost:8000/docs` to try it interactively, or
`http://localhost:8000/snapshot` directly.

## Deploying to Render — step by step

Render is used here because it runs a real persistent process (required
for the background scheduling loop and in-memory state) rather than
serverless functions, and has a usable free tier.

### 1. Push this backend to its own GitHub repo

Render deploys from a Git repo. If this backend lives in the same repo
as your frontend, that's fine too — you'll just point Render at this
subfolder in step 3.

### 2. Create a Render account

Go to [render.com](https://render.com) and sign up (GitHub sign-in is
easiest since you'll be connecting a GitHub repo anyway).

### 3. Create a new Web Service

- Dashboard → **New +** → **Web Service**
- Connect your GitHub account and select this repo
- If the backend is in a subfolder (not repo root), set **Root Directory** to that folder's path
- Render should auto-detect the `render.yaml` in this project and pre-fill:
  - **Build Command:** `pip install -r requirements.txt`
  - **Start Command:** `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
- If it doesn't auto-detect, enter those two commands manually
- **Instance Type:** Free is fine for a hackathon demo

### 4. Set the CORS environment variable

In the service's **Environment** tab, add:

```
CORS_ORIGINS = https://greenqueue.vercel.app,http://localhost:5173
```

(Add any other frontend URLs you need — comma-separated, no spaces.)

### 5. Deploy

Click **Create Web Service**. Render builds and starts it — takes a
couple of minutes the first time. When it's done, you'll get a URL like:

```
https://greenqueue-backend.onrender.com
```

### 6. Verify it's actually working

```bash
curl https://greenqueue-backend.onrender.com/health
curl https://greenqueue-backend.onrender.com/snapshot
```

The second command should return real JSON matching the shape shown
above — jobs, grid, impact, `"demoMode": false`.

### 7. Point the frontend at it

In your **Vercel** project (the `greenqueue-web` frontend), go to
**Settings → Environment Variables** and add:

```
VITE_API_BASE_URL = https://greenqueue-backend.onrender.com
```

Then redeploy the frontend (Vercel → Deployments → ⋯ → Redeploy, or
just push a new commit) so the env var takes effect — Vite bakes env
vars in at build time, so it won't apply until the next build.

### 8. Confirm end-to-end

Open `https://greenqueue.vercel.app/` and check the browser console —
if the backend call succeeds, there should be no "backend unreachable"
warning, and the dashboard's numbers should be the live ones from your
Render deployment rather than the bundled mock data.

## Deploying "over Firebase" — via Cloud Run

Firebase Hosting itself only serves static files — it can't run a
Python process. The real path for a custom backend "under Firebase" is
**Cloud Run**, which lives in the same Google Cloud project as your
Firebase project. This is the standard, Google-documented way to run a
custom backend alongside a Firebase app.

**Important trade-off, read before you start:** Cloud Run scales to
zero by default and only guarantees CPU *during* a request. This
backend has a background loop (ticks every 5s) and in-memory state that
need to persist between requests — with the default scale-to-zero
setting, the loop effectively pauses between requests and an instance
restart resets all job history. Step 6 below shows how to fix this by
setting **minimum instances = 1**, which costs a small continuous
amount (not free-tier eligible) rather than being free like Render's
equivalent trade-off.

### 1. Install the Google Cloud CLI

Follow [cloud.google.com/sdk/docs/install](https://cloud.google.com/sdk/docs/install)
for your OS, then:

```bash
gcloud init
```

Sign in and either select your existing Firebase project's underlying
GCP project, or create one — every Firebase project has a matching GCP
project of the same ID, visible in the Firebase Console under Project
Settings.

### 2. Enable the required APIs (one-time)

```bash
gcloud services enable run.googleapis.com artifactregistry.googleapis.com
```

### 3. Deploy from this folder

From inside the `greenqueue-backend/` directory (where the `Dockerfile`
is):

```bash
gcloud run deploy greenqueue-backend \
  --source . \
  --region us-central1 \
  --allow-unauthenticated \
  --set-env-vars CORS_ORIGINS=https://greenqueue.vercel.app,http://localhost:5173
```

- `--source .` tells Cloud Run to build the Dockerfile in this folder and push it — you don't need a separate `docker build`/`docker push` step, Cloud Run does it for you.
- `--allow-unauthenticated` makes the API publicly reachable (required — otherwise your frontend can't call it).
- Pick a `--region` close to your users; `us-central1` is a safe default.

This takes a few minutes the first time (building the image). When it
finishes, it prints a URL like:

```
https://greenqueue-backend-xxxxxxxxxx.us-central1.run.app
```

### 4. Verify it

```bash
curl https://greenqueue-backend-xxxxxxxxxx.us-central1.run.app/health
curl https://greenqueue-backend-xxxxxxxxxx.us-central1.run.app/snapshot
```

### 5. (Optional) Route it through your Firebase Hosting domain

If you want the API reachable at `https://your-project.web.app/api/...`
instead of the raw Cloud Run URL, add a rewrite to `firebase.json` in
your **frontend's** Firebase project (this repo's `firebase.json`, if
you're using the Firebase-hosted frontend rather than Vercel):

```json
{
  "hosting": {
    "rewrites": [
      {
        "source": "/api/**",
        "run": {
          "serviceId": "greenqueue-backend",
          "region": "us-central1"
        }
      }
    ]
  }
}
```

Then `firebase deploy --only hosting`. This step is optional — the raw
`*.run.app` URL works fine as `VITE_API_BASE_URL` on its own.

### 6. Fix the scale-to-zero problem (recommended for a live demo)

```bash
gcloud run services update greenqueue-backend \
  --region us-central1 \
  --min-instances 1 \
  --no-cpu-throttling
```

- `--min-instances 1` keeps one instance always warm, so your job
  history and background loop survive between requests.
- `--no-cpu-throttling` ("always allocated CPU") is what lets the
  background `asyncio.sleep` loop actually keep ticking between
  requests, not just during them.
- **This incurs an ongoing small cost** — Cloud Run's free tier assumes
  scale-to-zero. Check current pricing at
  [cloud.google.com/run/pricing](https://cloud.google.com/run/pricing)
  before enabling this if cost matters for your situation. For just a
  hackathon demo window, you can skip this and instead hit `/health` a
  minute or two before presenting to warm up a fresh instance, same as
  the Render approach — the trade-off is job history may reset if the
  instance recycles mid-demo.

### 7. Point the frontend at it

Same as the Render instructions above: set `VITE_API_BASE_URL` in your
frontend's hosting environment variables (Vercel, or Firebase env
config if you migrate the frontend there too) to whichever URL you're
using — the raw Cloud Run URL, or your Firebase Hosting domain + `/api`
if you set up the rewrite in step 5 — then redeploy the frontend.

## Deploying via GitHub Actions (push-to-deploy)

This sets up automatic deployment to Cloud Run every time you push to
`main` — no manual `gcloud` commands after the initial setup. The
workflow file is already in this repo at
`.github/workflows/deploy.yml`. This section is the setup you do once;
after that, `git push` is the entire deploy process.

### Step 1 — Push this backend to a new GitHub repository

If you haven't already:

```bash
cd greenqueue-backend
git init
git add .
git commit -m "Initial GreenQueue backend"
```

Create a new empty repository on GitHub (github.com → New repository —
don't initialize it with a README, since you already have one), then:

```bash
git remote add origin https://github.com/YOUR_USERNAME/greenqueue-backend.git
git branch -M main
git push -u origin main
```

### Step 2 — Enable the required Google Cloud APIs (one-time)

If you haven't done this already from the manual Cloud Run setup:

```bash
gcloud services enable run.googleapis.com artifactregistry.googleapis.com cloudbuild.googleapis.com iam.googleapis.com
```

### Step 3 — Create a dedicated service account for GitHub Actions

Don't reuse your personal `gcloud` login for this — create a scoped
service account instead, so GitHub only has exactly the permissions it
needs:

```bash
gcloud iam service-accounts create github-deployer \
  --display-name "GitHub Actions Cloud Run Deployer"
```

Note your project ID for the next commands:

```bash
gcloud config get-value project
```

### Step 4 — Grant that service account the roles it needs

Replace `YOUR_PROJECT_ID` in each command below with the value from
Step 3:

```bash
gcloud projects add-iam-policy-binding YOUR_PROJECT_ID \
  --member="serviceAccount:github-deployer@YOUR_PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/run.admin"

gcloud projects add-iam-policy-binding YOUR_PROJECT_ID \
  --member="serviceAccount:github-deployer@YOUR_PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/iam.serviceAccountUser"

gcloud projects add-iam-policy-binding YOUR_PROJECT_ID \
  --member="serviceAccount:github-deployer@YOUR_PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/artifactregistry.writer"

gcloud projects add-iam-policy-binding YOUR_PROJECT_ID \
  --member="serviceAccount:github-deployer@YOUR_PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/cloudbuild.builds.editor"

gcloud projects add-iam-policy-binding YOUR_PROJECT_ID \
  --member="serviceAccount:github-deployer@YOUR_PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/storage.admin"
```

What each role is actually for: `run.admin` deploys/updates the Cloud
Run service; `iam.serviceAccountUser` lets it act as the runtime
service account; `artifactregistry.writer` pushes the built container
image; `cloudbuild.builds.editor` submits the build (source-based
deploys use Cloud Build behind the scenes); `storage.admin` covers
Cloud Build's temporary staging bucket.

### Step 5 — Create and download a key for that service account

```bash
gcloud iam service-accounts keys create github-deployer-key.json \
  --iam-account=github-deployer@YOUR_PROJECT_ID.iam.gserviceaccount.com
```

This downloads a JSON file into your current folder. **Treat this file
like a password** — anyone with it can deploy as this service account.

### Step 6 — Add it to GitHub as a repository secret

On GitHub: your repo → **Settings** → **Secrets and variables** →
**Actions** → **New repository secret**.

Create two secrets:
- **Name:** `GCP_SA_KEY` — **Value:** paste the entire contents of `github-deployer-key.json`
- **Name:** `GCP_PROJECT_ID` — **Value:** your project ID (from Step 3)

### Step 7 — Delete the local key file

Once it's pasted into GitHub Secrets, delete it from your machine —
there's no reason for it to exist as a file anymore:

```bash
rm github-deployer-key.json
```

(It's also listed in `.gitignore` already, so it won't get committed by
accident, but delete it anyway rather than relying on that.)

### Step 8 — Push to trigger the first deployment

```bash
git add .
git commit -m "Add Cloud Run deploy workflow"
git push
```

### Step 9 — Watch it deploy

On GitHub: your repo → **Actions** tab → click the running workflow.
You'll see live logs for each step (checkout, auth, gcloud setup,
deploy). The final step prints the deployed URL — something like
`https://greenqueue-backend-xxxxxxxxxx.us-central1.run.app`.

If it fails, the logs will tell you which step — the most common first-time
issues are a missing IAM role (re-check Step 4) or an API that wasn't
enabled (re-check Step 2).

### Step 10 — Point your frontend at the deployed URL

Same as before: Vercel → your frontend project → Settings →
Environment Variables → set `VITE_API_BASE_URL` to the Cloud Run URL
from Step 9 → redeploy the frontend.

### From now on

Every `git push` to `main` re-deploys automatically. No more manual
`gcloud` commands. If you need to change the CORS origins or other
settings, edit `env_vars` in `.github/workflows/deploy.yml` and push —
that's now the one place deployment config lives.

### Security note

The service-account-JSON-key approach above is the simplest to set up
correctly by hand, which is why it's the one detailed here — but it is
a long-lived credential sitting in GitHub's secret store. For anything
beyond a hackathon project, Google's recommended approach is **Workload
Identity Federation**, which lets GitHub Actions authenticate without
any stored key at all (GitHub proves its identity via OIDC tokens
instead). It's a more involved one-time setup — see
[Google's guide](https://github.com/google-github-actions/auth#setting-up-workload-identity-federation)
if you want to harden this later. Not required to get this working now.
